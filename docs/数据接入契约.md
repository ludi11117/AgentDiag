# 数据接入契约

> **一句话**：把 `data/knowledge_base.txt` 换成你自己的资料，系统就按你的资料答。
> 但"灌进去"和"被读懂"是两件事——本文说明系统**读得懂**的写法，以及为什么。

## 一、先跑自查（30 秒）

填完数据、构建之前，**先跑这一条**：

```bash
venv/Scripts/python.exe tools/validate_knowledge_base.py
```

它会告诉你：解析出多少条『可能原因』、覆盖几个章节、有没有哪一类写法没被识别。
输出 `✓ 解析出 N 条` 才算通过；`✗ 不合格` 表示**别急着构建**。

想校验别的文件（比如还没替换进来的草稿）：

```bash
venv/Scripts/python.exe tools/validate_knowledge_base.py 我的资料.txt
```

再构建（幂等，可重复跑）：

```bash
venv/Scripts/python.exe build_knowledge_base.py            # 默认先清空再写入
venv/Scripts/python.exe build_knowledge_base.py --dry-run  # 只看切分，不写库、不调模型
```

## 二、为什么格式这么重要：一个**静默**失效

系统里有一条护栏叫**排除条件映射**。用户报修时说"轴承刚换过，别往轴承方向查"，
系统要能把"轴承"映射到知识库里的具体原因条目，然后在诊断时把它们整条剔掉。

这个映射的候选集，来自对知识库文本的解析（`agents.extract_kb_causes()`）。
**如果解析结果为空，映射会直接返回空列表**——于是：

> 系统照样跑出诊断、照样出工单，看起来一切正常，
> 但**用户说的"已排除某某"不再被遵守**，而且**没有任何一处报错**。

这就是为什么必须有格式约定：它不是文风偏好，而是护栏的**输入前提**。
（2026-09-18 实测：现有知识库用标准格式解析出 104 条；换成 Markdown 无序列表
或 Excel 导出格式，旧版解析结果为 **0 条**。）

## 三、认得的写法

### 章节标题（用来区分设备/故障条目）

```text
一、主轴电机报警代码E-203          ← 中文序号
## 主轴电机 E-203                  ← Markdown 标题（# 到 ###### 都行）
```

章节名会作为"条目归属"，用于**按设备收窄**。不写也能解析，但会触发提醒——
因为没有归属的条目可能被跨设备误排除。

### 『可能原因』条目（**核心**，必须有）

写在小节名 `可能原因：` 之后，或**直接跟在设备标题下**：

```text
可能原因：                          ← 小节名（可省略，见下）
1. 主轴电机负载过大或负载不平衡。    ← 半角点
2. 主轴轴承损坏或润滑不良。
```

也可以写成这些等价形式，都会识别：

| 写法 | 例子 |
|---|---|
| 半角点 | `1. 主轴轴承损坏` |
| 中文顿号 | `1、主轴轴承损坏` |
| Markdown 无序列表 | `- 主轴轴承损坏` / `* 主轴轴承损坏` / `• 主轴轴承损坏` |
| 带键名（Excel 导出常见） | `可能原因：主轴轴承损坏` 或 `可能原因<TAB>主轴轴承损坏` |
| 省略小节名 | 设备标题下直接跟 `1. …` `2. …` |

Markdown 装饰会被自动抹掉：`**主轴轴承损坏**` 与 `主轴轴承损坏` 视为同一条。

### 其他小节（`故障现象` / `排查建议` / `经验分歧` …）

这些小节**不会被当成原因**，写不写都行。系统能识别它们，并把它们排除在候选集之外
——否则"检查加工程序"这类**处置措施**会混进原因候选，让排除映射张冠李戴。

### 完整的、被推荐的写法

```text
【数控机床主轴电机常见故障与排查】

一、主轴电机报警代码E-203
故障现象：主轴转速不稳定，伴有异常噪音，电机温度快速升高。
可能原因：
1. 主轴电机负载过大或负载不平衡，导致电机过载发热。
2. 主轴轴承损坏或润滑不良，导致转动阻力增大。
3. 电机冷却系统故障，导致散热能力下降。
排查建议：
- 检查加工程序，确认是否存在过重切削或负载不平衡。
- 检查主轴轴承磨损情况和润滑脂状态，必要时更换轴承。
经验分歧：
- 张师傅认为E-203八成是负载问题，先查程序最省事。
- 李师傅坚持先拆轴承，理由是"报E-203时轴承往往已经伤了"。
```

`经验分歧` 这一段是**本项目有意保留**的：真实场景里老师傅的判断本来就常不一致，
而这正是系统采用多 Agent 辩论的理由——单 Agent 面对两派矛盾意见，只能二选一、
和稀泥或编个折中，三种都是失真。详见 `docs/为什么必须多Agent.md`。

## 四、备件价格表（可选，影响成本核算）

在 `config.py` 的 `PARTS_PRICE` 里补自己厂里的备件单价：

```python
PARTS_PRICE = {
    "主轴轴承": 850,
    "液压泵": 2500,
    # 加你的备件…
}
```

**没在表里的备件会显式提示"未覆盖"，不会静默不计费**——这是有意的：
模型只负责指出要换什么，算钱一律走 `calculate_cost()` 这个纯函数，不交给模型心算。

## 五、接入清单

- [ ] 按上面格式写好资料，替换 `data/knowledge_base.txt`
- [ ] `python tools/validate_knowledge_base.py` → 看到 `✓ 解析出 N 条`
- [ ] `python build_knowledge_base.py --dry-run` → 确认切分块数合理
- [ ] `python build_knowledge_base.py` → 真正写入向量库
- [ ] **确认块数 > 0**（脚本会打印；本脚本是"先清后写"，失败会留下空库）
- [ ] 重启后端服务（运行中的进程持有旧索引）
- [ ] 备件价格表按需补 `config.py: PARTS_PRICE`
- [ ] （可选）照 `test_cases.json` 的格式，给你自己的数据配一批用例

## 六、常见问题

**Q：我有几百页 PDF 手册，能直接灌吗？**
A：要先转成上面的文本格式。直接灌整段 PDF 文本大概率解析不出条目——
用 `tools/parse_manual_pdf.py` 可以参考怎么从 PDF 抽结构化条目，但**抽完要人工核对**：
手册里的「处理」字段常常是 `--`（让通知服务部门），那不是维修指导。

**Q：我把数据换成自己的，评估指标会不会掉？**
A：**会，而且这本身是有用信息**。`test_cases.json` 里的黄金根因原本是锚在
旧知识库措辞上的，换库后它们未必还能在库里找到依据。改完库务必跑：

```bash
venv/Scripts/python.exe -m pytest tests/test_eval_dataset.py -q
```

这个测试专门断言"黄金根因必须在知识库里有依据"——它红了说明**你在用库外的答案
考系统**，得同步调整用例，而不是无视它。

**Q：想省事，能不能不写 `可能原因：` 小节名？**
A：可以，设备标题下直接跟 `1. …` 列表就认。但**纯符号列表（`-` / `*`）在没写
小节名时不会被收**——因为那种写法在"排查建议"下同样常见，盲收会把处置措施
当成原因。这是个刻意的方向性取舍（宁可漏收符号列表，也不误收处置措施）。
