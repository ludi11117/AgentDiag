# 为什么必须是多 Agent

> 这份文档回答面试中最容易被追问、也最容易答砸的一个问题：
> **"你这里为什么要用多 Agent？单 Agent 不也能做吗？"**
>
> 全文的每个论断都标注了代码位置。不要背结论，去读代码——面试官会追问细节。

---

## 一、先排除错误的理由

以下说法听起来正当，但**经不住追问**，建议不要作为主要论据：

| 常见说法 | 为什么站不住 |
|---|---|
| "多 Agent 分工，效率更高" | 追问："哪个环节单 Agent 做不到？"——分工本身不构成必要性，一个 Agent 顺序调用几个 prompt 也能分工。 |
| "多 Agent 更准确" | 追问："有数据吗？"——**没有对比实验前，这是断言不是证据**。缺口见第五节。 |
| "工业场景复杂，需要多角色" | 追问："复杂在哪？"——"复杂"是形容词，不是机制。 |
| "用了 LangGraph，所以是多 Agent" | 框架选择是结果不是理由。追问"为什么不用 LCEL 串起来"就答不上来了。 |

**核心问题**：以上都是"多 Agent 有什么好处"，而面试官真正在问的是"**为什么单 Agent 在这里会失败**"。

---

## 二、真正的理由：单 Agent 结构性地缺少"反对者"

### 2.1 问题的本质是"自我批卷"

单 Agent 的默认形态是：**同一个模型、同一个上下文，先写答案，再检查自己的答案**。

这在机制上有两个无法绕开的缺陷：

1. **沉没成本**：它刚刚生成了这个答案，检查时倾向于认定其正确。让它否定自己，等于要求它推翻上文刚说过的话——语言模型的生成是条件于上文的自回归过程，**推翻上文需要极强的显式指令**，而"温和地检查一下"这种指令强度不够。
2. **同一视角**：检查者和被检查者共享同一套错误前提。如果它一开始就误判了设备类型，它不会在自检时发现——因为自检用的还是那个错误前提。

**这不是"能力不够"，是结构问题。** 换更大的模型也解决不了：更大的模型会在那个错误前提上**更自信地**推理。

### 2.2 本项目的解法：四个结构性隔离

代码里对抗性不是靠"提示词里写一句请严格审核"实现的，而是靠**上下文隔离**——每个 Agent 拿到的输入是**前一个 Agent 的结构化输出**，而不是完整的历史对话：

| 隔离点 | 位置 | 隔离了什么 |
|---|---|---|
| 审核师看不到诊断师的推理过程 | `orchestrator.py:216` `review_node` → `agent_review(state["diagnosis"])` | 只传结论。诊断师"我觉得可能是……"的犹豫过程不会污染审核师。 |
| 审核师有独立的驳回权 | `orchestrator.py:216-223`，不通过则 `status="reviewed"` 走辩论分支 | 审核师不是"确认按钮"，它的输出会**改变图的路由**。 |
| 辩论必须重新取证 | `orchestrator.py:242-246` | 辩论不是让两个模型互相说服，而是**拿着审核意见去重新检索**（`targeted_query = fault_str + 审核理由`）。 |
| 复审独立于首审 | `orchestrator.py:287` `_effective_review` | 辩论翻盘后由 `final_review` 重新裁决，而不是沿用首审的"不通过"。 |

**其中最值得讲的是第三个**：

```python
# orchestrator.py:242-246
targeted_query = fault_str
if latest_feedback and latest_feedback.get("理由"):
    targeted_query = fault_str + " " + latest_feedback["理由"]
new_evidence = retrieve_evidence(targeted_query, k=settings.RETRIEVAL_K, ...)
```

驳回理由被当作**检索 query** 使用。也就是说：审核师说"你没有考虑轴承磨损"，系统不是让诊断师"再想想"，而是**带着"轴承磨损"这个关键词去知识库重新捞一遍资料**。

这一手把辩论从"两个模型互相说服"（不可证伪、容易和稀泥）变成了"**针对争议点补充证据**"（可追溯、可验证）。**这是本项目多 Agent 设计里最实的一块。**

## 三、第二个理由：经验本身是冲突的，单一结论是失真

这是「经验库」改造带来的新论据，也是**最能体现领域理解的一条**。

### 3.1 知识库里的冲突是刻意保留的

打开 `data/knowledge_base.txt`，同一个故障下会有互相矛盾的说法。例如 `主轴电机报警代码E-203`：

```
经验分歧：
- 张师傅（12年机床维修）认为E-203八成是负载问题，先查程序最省事。
- 李师傅（18年经验）坚持先拆轴承，理由是"E-203报出来时轴承往往已经伤了，只查程序拖两天会更贵"。
- 两人一致的地方：冷却系统必须一起看，因为散热不良会让前两个问题互相加重。
```

### 3.2 单 Agent 拿到这种材料必然失真

面对"张师傅说 A、李师傅说 B"，单 Agent 只有三种处理方式，**三种都是失真**：

1. **二选一**——丢掉另一半信息，且选择是随机的（取决于哪个说法在上下文里更靠前）。
2. **和稀泥**——输出"A 和 B 都有可能"，看似客观，实际是把判断责任推给用户。
3. **编一个折中**——最糟，凭空制造一个知识库里不存在的第三种说法（**这就是幻觉**）。

**多 Agent 才有可能正确表达"这是两派意见"**：诊断师给一个倾向性判断，审核师从另一派立场挑战它，辩论环节把双方依据都摆出来，最终结论里保留分歧。

> ⚠️ **诚实标注**：这一条目前是**设计意图 + 材料准备就绪**，但**尚未用实验验证**"多 Agent 在冲突材料上确实比单 Agent 好"。验证方式见第五节。

## 四、第三个理由：可靠性需要独立的裁决者，而不是自我担保

这条与"诊断准确性"无关，但工程上很硬。

`orchestrator.py:38`：

```python
TERMINAL_FAILURE_STATUSES = ("insufficient_knowledge", "llm_failed", "pending_human_review")
```

单 Agent 架构下，如果模型调用失败或知识库没依据，输出要么是空的、要么是编的——**没有任何一个环节有资格说"我这次不可靠"**，因为说这话的正是可能已经出问题的那个组件。

多 Agent 里，终态失败是一个**独立于诊断结论的通道**：

| 终态 | 触发位置 | 含义 |
|---|---|---|
| `insufficient_knowledge` | 检索无依据 / `rebuttal_node` 兜底 | 知识库没有依据，不编 |
| `llm_failed` | 任一节点返回 `None` → 短路 | 调用失败，不把空结果流下去 |
| `pending_human_review` | `orchestrator.py:350-363` 复审未通过 | 有结论但存疑，交人工 |

而且 `orchestrator.py:229` 有一条专门的防线：

```python
if _is_degraded(state.get("diagnosis")):
    return {"rebuttal": {}, ..., "status": "insufficient_knowledge"}
```

**已经诚实降级的诊断，绝不允许在辩论环节被"越辩越有信心"地编出根因来。** 这条兜底的存在说明设计者意识到：辩论有把"不知道"变成"知道"的倾向，必须显式拦住。

这个论点的价值在于：它**不依赖"多 Agent 更准"**，即使多 Agent 准确率没有提升，这条可靠性理由依然成立。面试时如果被质疑"多 Agent 增益不明显"，这是可以退守的阵地。

## 五、当前缺口：没有对比实验的数据

**这是最大的窟窿，必须补。**

现在如果面试官问"你凭什么说多 Agent 好"，能答的只有"设计上更合理"。**没有数字。**

补法：`ablate_single_vs_multi.py`（本仓库）

- 单 Agent 基线：`抽取 → 检索 → 一次诊断`，无审核、无辩论、无 schema 回灌
- 多 Agent：走真实 LangGraph 全流程
- **两侧用同一套判定函数、同一份 evidence**，保证可比
- 输出 6 项指标对照：核心一致率 / 全覆盖率 / 幻觉率 / 排除遵守率 / 诚实降级率 / 误降级率

```bash
python ablate_single_vs_multi.py --limit 5    # 先小样本验证
python ablate_single_vs_multi.py              # 全量 30 例（会消耗 API 额度）
```

**报告位置**：`eval_reports/ablation_<时间戳>.md` / `.json`

### 结果可能出现三种情况，都要如实面对

| 结果 | 含义 | 该怎么讲 |
|---|---|---|
| 多 Agent 明显更优 | 架构有效 | 直接给数字，并说明在哪类用例上增益最大 |
| 无明显差异 | **架构的增益没有被这套题测出来**，可能是题目太简单（多为报警码直查型） | 诚实说：在"答案唯一"的题上多 Agent 没有优势；增益应该出现在冲突材料、排除条件、知识库外这三类对抗题上——做分层统计 |
| 多 Agent 更差 | 辩论引入了噪声 | **这是最有价值的发现**。说明辩论在"简单题"上会画蛇添足（把对的改成错的）。讲法：这暴露了辩论触发条件需要收紧——只在审核不通过时才辩论，而目前审核的判据太松 |

> 第三种情况在 `--limit 2` 的预跑里已经露出苗头：TC002 多 Agent 在正确答案之外多出了一个"编码器信号异常"，且辩论了 3 轮。**宁可把这个现象讲清楚，也不要藏。**

## 六、面试怎么讲（30 秒版）

> "单 Agent 的问题不是能力不够，是**没有反对者**。让它自己检查自己，它倾向于认为刚才写的答案是对的——这是自回归生成的结构性问题，换更大的模型只会让它更自信地在错误前提上推理。
>
> 我的做法是把对抗做成结构：审核师拿不到诊断师的推理过程，只能看结论，它的输出会改变流程走向；**驳回理由会被当成检索关键词重新捞资料**，所以辩论不是两个模型互相说服，而是针对争议点补证据。另外我的知识库里刻意保留了 34 处老师傅的经验分歧，单 Agent 遇到'张师傅说 A、李师傅说 B'只能二选一或和稀泥，多 Agent 才有可能如实表达'这是两派意见'。
>
> 我还写了消融实验脚本对比单/多 Agent 的六项指标——**数字在 `eval_reports/ablation_*.md` 里**，包括多 Agent 表现更差的用例我也留在报告里，因为那说明辩论的触发条件需要收紧。"

**最后那句话是关键**：主动承认架构的局限，比声称它处处更好更可信。
