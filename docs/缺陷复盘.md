## 缺陷一：排除条件被静默丢弃（已修复）

### 现象

用例 TC018 问：变频器 F-014 报接地故障，用户补充两个前提——
「电机绕组对地绝缘**测量正常**」「电缆护套**完好**」，即明确排除了两条根因。
系统最终输出的根因里，却仍然写着「**动力电缆在桥架转弯处磨损露出导体**」。

即：**用户明确说"我查过了、没问题"的那一项，被系统当成根因写回去了。**

### 定位过程

先拆开抽取环节，确认信息有没有抽出来：

```
抽取结果:
  排除条件: ['电机绕组对地绝缘测量正常', '电缆护套完好']   ← 抽取是对的
  故障现象: ['变频器报接地故障', '无法正常启动']
```

抽取阶段没问题，说明缺陷在下游的**排除映射**环节。
继续往下探，打印检索到的候选原因与映射结果：

```
检索到 3 条候选原因:
  [0] 电机绕组对地绝缘破损。
  [1] 动力电缆在桥架转弯处磨损露出导体。   ← 用户已排除，但没被映射到
  [2] 变频器内部电流互感器故障造成误报。

映射到的排除编号: [0]      ← 只映射了 1 条，应该是 [0, 1]
```

到这里缺陷锁定：**映射环节漏了第二条。**

### 根因（两层）

看 `agents.py::map_excluded_causes` 的原始实现，问题有两层：

**第一层：确定性兜底被短路了**

```python
idx = sorted({n - 1 for n in numbers if n - 1 in scope})

if not idx:                          # ← 缺陷在这里
    for excl in exclusion_list:      # 确定性 token 重叠匹配
        ...
```

`if not idx:` 的含义是：**只要 LLM 返回了任意一个编号，整段确定性匹配就跳过。**
本例中 LLM 返回了 `[0]`，于是确定性匹配根本没跑，第二条排除项失去了唯一的补救机会。

这是个很隐蔽的错误：它看起来像"有 LLM 就不需要兜底"的正常设计，
但实际语义是"**LLM 只要答对一部分，剩下的就没人管了**"。

**第二层：即使跑了兜底，判据也偏弱**

原兜底是"取该排除项得分最高的那一条原因"。实测各组合的 token 命中数：

| 排除描述 | vs 目标原因 | 命中 token |
|---|---|---|
| 电机绕组对地绝缘测量正常 | 电机绕组对地绝缘破损 | 3 个（电机、绕组、绝缘） |
| 电缆护套完好 | 动力电缆在桥架转弯处磨损露出导体 | **1 个（电缆）** |

第二条只能命中 1 个 token，因为排除描述里的「护套、完好」在原因条目里都不存在，
而原因条目里的「动力、桥架、转弯、磨损」在排除描述里也没有。
**排除描述与原因条目本来就常常只有一个词重合**——这是自然语言的正常现象，不是数据问题。
另外「正常 / 完好 / 测量」这类词会撑大排除描述的 token 集合，稀释真正有指向性的词。

### 修法

改 `agents.py`，两处：

1. **确定性匹配从"兜底"改为"始终执行、与 LLM 结果取并集"**：

```python
idx = sorted(set(idx) | set(_deterministic_exclusion_hits(exclusion_list, kb_entries, scope)))
```

这里做了一个**明确的方向性取舍**：宁可多排除，不可漏排除。
因为排除条件是**用户的硬约束**——漏掉一条，等于把用户刚验证过没问题的原因又当成根因写回去，
用户会照着错误方向去拆机；多排除一条，最坏情况是少列一条候选，
而知识库条目本身还会在"排查建议"里被看到。**两者代价不对称，所以取并集。**

2. **新增 `_deterministic_exclusion_hits()`，逐条排除项各自找最佳匹配**，
   并加停用词表剔除「正常/完好/测量/已确认」这类不携带指向性的词：

```python
_EXCLUSION_STOPWORDS = frozenset({"正常", "完好", "良好", "测量", "测试", "确认", ...})

def _deterministic_exclusion_hits(exclusion_list, kb_entries, scope):
    hits = []
    for excl in exclusion_list:                    # 逐条排除项，各自独立匹配
        excl_tokens = _exclusion_tokens(excl)      # 已剔除停用词
        if not excl_tokens:
            continue
        best_i, best_hit = -1, 0
        for i in scope:
            cause_tokens = set(jieba.cut(kb_entries[i][1]))
            hit = sum(1 for t in excl_tokens if t in cause_tokens)
            if hit > best_hit:
                best_hit, best_i = hit, i
        if best_i != -1:
            hits.append(best_i)
    return hits
```

关键设计：**对每条排除项都得出一个结果**，不再让"某条整体被漏掉"发生。
判据只要求命中 token 数 > 0，**不设比例阈值**——按比例卡的话，
「电缆护套完好」只命中 1/3 就会被全部漏掉，而漏排除正是要修的问题。

### 验证

修复后的确定性映射：

```
排除命中: [0, 1]   ← 期望 [0, 1]，通过
LLM=[0] ∪ 确定性=[0,1] -> [0, 1]
```

并补了离线单测（不花 API 额度），并做了**退化验证**：
把修复临时换回 `if not idx:` 写法，确认测试会失败，再换回。

## 缺陷二：多 Agent 协作中候选根因被静默收敛（已修复）

### 现象

用例 TC021 问：离心泵启动后压力表无读数、出口无流量，且已排除「气缚」。
黄金答案剩 3 条根因，系统最终只给了 2 条，丢掉了「**吸入高度超过允许吸上真空高度**」。

评估里体现为：**核心一致率 100%（宽松），但全覆盖率 87.5%**——
即"至少答对一条"过关，"是否答全"不过关。

### 定位过程

先排除"检索没检到"这个最可能的嫌疑：

```
检索到 4 条候选原因:
  [0] 泵体内未灌满液体，发生气缚。          ← 被正确排除
  [1] 吸入管路漏气或底阀失效。
  [2] 电机转向与泵要求方向相反。
  [3] 吸入高度超过允许吸上真空高度。        ← 在检索结果里！
```

**第三条根因明明在检索资料里**，所以不是检索截断（`RETRIEVAL_K=3` 的嫌疑排除）。

再单独跑初诊：

```
初诊根因: 原因1：吸入管路漏气或底阀失效；原因2：电机转向与泵要求方向相反；原因3：吸入高度超过允许吸上真空高度
```

**初诊是完整的三条**，而且「气缚」被正确排除了。缺陷发生在**初诊之后**。

对比初诊与终诊：

```
初诊: 原因1：吸入管路漏气或底阀失效；原因2：电机转向与泵要求方向相反；原因3：吸入高度超过允许吸上真空高度
终诊: 吸入管路漏气或底阀失效；电机转向与泵要求方向相反      ← 丢了第三条
辩论轮次: 1
```

**辩论（rebuttal）阶段把候选收敛掉了。**

### 根因（跨 Agent 的约束不一致）

对比两个提示词，问题一目了然：

| | 诊断 `agent_diagnose.j2` | 辩论 `agent_rebuttal.j2` |
|---|---|---|
| 是否要求保留全部候选 | **有**，写得很硬 | **没有，一条都没有** |
| 原文 | "你必须把【资料】中'可能原因'部分列出的**每一项**，按原文顺序**全部写入**"<br>"即使你认为某项可能性较低，**也必须列入，不得自行取舍**" | 只要求"选择行动之一：反驳 / 修正"，输出 `最终根因` 字段 |

诊断阶段有"不得自行取舍"的硬约束，**辩论阶段没有任何等价约束**。
于是辩论成了一个"合法丢失信息"的缺口：
模型在被驳回后倾向于"收敛到一个更聚焦的结论"，而提示词没有禁止它这么做。

更值得注意的是：**辩论节点会换一个查询重新检索**（`targeted_query = fault_str + 审核理由`），
检索结果变了，prompt 里也没要求它对齐初诊的条目集合——
两边的"候选原因清单"可能根本不是同一个集合，却要求辩论产出最终根因。

### 为什么这个缺陷值得单独讲

它不是"某处写错了一个判断"，而是**多 Agent 系统里典型的约束漂移**：
同一个语义要求（"候选原因要保全集，不能丢"）在链路的一环存在、在另一环缺失，
于是系统从**后端**漏掉了信息，而**每个 Agent 单独看都做对了**。

单测也很难覆盖它——因为每个 Agent 的入参出参都合法，
只有把「初诊 → 审核 → 辩论 → 终诊」串起来跑真实状态机，才会暴露。

### 修法（已实施）

按上面的取舍，选了 **方案 2 + 方案 3 的组合**：确定性护栏兜底，不改提示词。

新增 `agents.restore_dropped_candidates()`，接在 `agent_rebuttal` 末尾：

```python
# 护栏：辩论不得把初诊里"有依据且未被排除"的候选静默丢掉
if result_dict.get("最终根因") and diagnosis.get("根因判断"):
    result_dict["最终根因"] = restore_dropped_candidates(
        diagnosis["根因判断"], result_dict["最终根因"], exclusion_list
    )
```

判定逻辑：把初诊与终诊都拆成候选列表，对初诊里**每一条**判断——

| 情况 | 处理 |
|---|---|
| 终诊里已有完全相同的条目 | 不动 |
| 该条命中用户排除条件 | **不补回**（用户排除过的不能复活） |
| 与终诊某条互为包含（语义重复） | 不补回（算仍被覆盖） |
| 其余（初诊有、终诊没有、也没被排除） | **补回到终诊末尾** |

`assert` 不在业务逻辑里，只在开发期校验降级标记同步（见下）。

### 验证（离线，可复现）

`tests/test_guards_and_pagination.py` 新增 12 条针对性回归测试，全量 192 条全绿。
关键是**每一条都做了退化验证**（把修复换回旧写法，确认测试真的失败）：

| 退化注入 | 预期失败 | 实测 |
|---|---|---|
| 断开 `agent_rebuttal` 里的护栏接线（`if False and ...`） | 接线测试 | ✅ `护栏没接上 agent_rebuttal：'原因1：密封件老化开裂'` |
| 把降级判定挪到"拆分候选之后" | 4 条降级保护测试 | ✅ 见下方专节 |
| 从 `agents` 侧删掉一个降级标记 | 同步测试 | ✅ `agents 侧缺少降级标记：['不相关']` |
| 去掉"已排除不补回"分支 | 排除项测试 | ✅ |
| 去掉"包含即算覆盖"分支 | 重复误判测试 | ✅ |

> 这次退化验证**救回了一个真实事故**（见下），也是全会话里最有价值的一步。

### ⚠️ 我写的护栏差点打穿诚实降级防线（子缺陷）

护栏第一版是这样的：

```python
if "【知识库无相关依据】" in (final_root or ""):    # ← 两个错
    return final_root
initial = _candidate_causes_of(initial_root)      # ← 判定被放在拆分之后
final   = _candidate_causes_of(final_root)
```

实测跑一遍，输入 `initial="原因1：密封件老化开裂；原因2：轴颈磨损…"`、
`final="知识库无相关依据，无法诊断"`，返回值是：

```
'知识库无相关依据; 无法诊断; 吸入管路漏气或阀失效; ...'
```

**每一张降级工单都会被编造出根因。** 两个独立的错误叠加：

1. **匹配串抄错了**：实际降级文案是 `知识库无相关依据，无法诊断`，
   **没有 `【】` 括号**——照抄了一个不存在的格式，判定永远为假。
2. **顺序错了（更隐蔽）**：降级文案里含**全角逗号**，`_candidate_causes_of`
   按 `[;；,，]` 拆分，`知识库无相关依据，无法诊断` 被切成两段。
   于是"逐片判断是否是降级文本"全部落空——每一片单独看都不含完整降级标记。

修法：抽出 `_DEGRADED_MARKERS` + `_is_degraded_text()`，
**把判定提到拆分之前**，并统一检查 `initial_root` 与 `final_root` 两侧：

```python
# 注意：判定必须在**拆分候选之前**做——降级文句里含全角逗号，
# 拆完会被切碎，再逐片判断就漏了（实测踩过）。
if _is_degraded_text(final_root) or _is_degraded_text(initial_root):
    return final_root
```

对应 4 条参数化测试钉住这个顺序，且都做了退化验证
（把判定挪回拆分之后 → 4 条全红）。

### ⚠️ 附带发现的第二处隐患：降级标记两份副本会漂移

`agents` 不能用 `orchestrator.DEGRADED_MARKERS`——`orchestrator` 反向依赖 `agents`，
会循环 import。所以标记在 `agents` 里手工复制了一份，这就有**静默漂移**风险：
哪天往正本里加一个标记、忘了同步副本，"降级不得改写"的判定就漏一个，
而且只有当某种降级文句恰好走到辩论路径上才暴露。

处理：

```python
def _assert_degraded_markers_in_sync() -> None:
    try:
        from orchestrator import DEGRADED_MARKERS as _canonical
    except Exception:
        return                       # 冷启动路径（orchestrator 尚未加载）安全降级
    missing = [m for m in _canonical if m not in _DEGRADED_MARKERS]
    assert not missing, f"agents._DEGRADED_MARKERS 与 orchestrator 不同步，缺失：{missing}"
```

在 `_is_degraded_text` 首次调用时校验一次（`_DEGRADED_SYNC_CHECKED` 标记），
再加一条显式断言测试，保证即使守卫的触发条件变了，漂移也会被抓住。

> **小注**：这里踩了个 Python 自身的坑——在函数里写 `_DEGRADED_SYNC_CHECKED = True`
> 会让它变成**局部变量**，前面的 `if not _DEGRADED_SYNC_CHECKED` 直接
> `UnboundLocalError`。得加 `global`。11 条测试当场全红，属于"跑一遍就发现"的那类。

### 这条缺陷的额外教训——测试别只测"算术"

给缺陷一写回归测试时，我第一版是这样写的：

```python
def test_exclusion_detection_survives_llm_partial_answer():
    llm_idx = [0]
    det = agents_module._deterministic_exclusion_hits(...)
    assert sorted(set(llm_idx) | set(det)) == [0, 1]     # ← 只断言了并集算术
```

**它在修复前和修复后都通过**——因为它没有触及 `map_excluded_causes` 里
那句 `if not idx:`。退化验证（把修复换回旧写法再跑）立刻暴露了这一点。

正确写法是**桩掉 LLM、驱动被测函数本身**：

```python
monkeypatch.setattr(agents_module, "invoke_and_parse_json",
                    lambda *a, **kw: {"排除编号": [1]})   # LLM 只答对一半
agents_module._exclusion_cache.clear()
idx = agents_module.map_excluded_causes([...], entries, scope=[0, 1, 2])
assert idx == [0, 1]
```

改完再退化验证，才真正失败：

```
AssertionError: LLM 漏掉的排除项未被补救：[0]
assert [0] == [0, 1]
```

> **这是一条反复出现、值得单独记住的规律**（本次会话里踩了两次）：
> 写"修复的回归测试"时，要断言**被测函数在真实调用路径上的行为**，
> 而不是把修复的逻辑**在测试里重抄一遍**。抄一遍等于测试自己证明自己，
> 永远绿，永远无用。
>
> 同一规律在缺陷二里又用了一次：护栏测试不能只断言
> `restore_dropped_candidates("A;B", "A") == "A; B"`——
> 那测不到"护栏有没有接在 `agent_rebuttal` 上"。
> 所以专写了一条 `test_agent_rebuttal_guard_is_wired_in`，
> 桩掉 `invoke_and_validate` 后驱动真实 `agent_rebuttal`。

## 这次复盘最值得讲的经验

### 1. 指标满分可能只是题目太简单

扩库前评估报告是：核心一致率 **100%**、幻觉率 **0%**、排除条件遵守率 **100%**。
看起来完美。但真实情况是：

- 知识库只有 **8 个向量块**，而 `RETRIEVAL_K=3` ——相当于**把整个库的 37% 直接喂给模型**，
  检索不可能失败；
- 32 条用例里只有 3 个主题，且 7/8 带报警码直查，**模型想编造都难**；
- 排除条件只有 3 条，且都是"某词不在库里"的简单情形。

**满分是数据规模与用例设计共同造成的假象。**
扩库到 30 例后：排除条件遵守率立刻掉到 **66.7%**、全覆盖率掉到 **87.5%**——
这两个"下降"才是真正有价值的信号，说明指标终于开始测量了。

### 2. 幻觉检测本身也曾"作弊"

原实现判断幻觉用的是**整份知识库的子串匹配**：

```python
if candidate in KB_TEXT:   # 整库子串
    return True
```

它的语义是"这句话在库里的**任何位置**出现过就算接地"。
于是**知识库越小，越容易碰巧命中，指标越漂亮**——1.5 KB 的库下幻觉率恒为 0，
完全没有测量意义。改成比对**本次检索命中的片段**后，口径才真实。

> 这里有个通用教训：**评估指标本身也需要被审计**。
> 一个"看起来 0% 缺陷"的指标，可能只是在测量一个注定为 0 的东西。

### 3. 只测函数本身，抓不住"漏传参数"

给幻觉检测加严格口径后，我写了 3 条测试，全绿。
但把严格口径改回宽松、再跑一遍——**3 条依然全绿**。

原因是那 3 条测的是**函数本身**（直接调 `is_hallucinated`），
而真正的风险是**评估流程忘了把 `evidence` 传进去**（调用点写错）。
补了一条专门盯调用点的测试后，退化验证才生效（`assert False is True`）。

> **规律：修复分"函数改对了"和"调用点接对了"两件事，测试必须分别覆盖。**

### 4. 方法名/文档字符串不是"修复还在"的证据

本项目有多个会话交替编辑，曾出现同名但语义不同的函数。
判断某处是否真修好，必须**把函数体读出来逐行看**，
并补一条"未修复时会失败"的断言——否则测试可能只是装饰。

### 5. 修复要选对方向，因为代价不对称

缺陷一里我选择"宁可多排除，不可漏排除"。
这不是技术偏好，而是**依据后果严重性做的取舍**：
漏排除 → 用户照错误方向拆机；多排除 → 少列一条候选。
两者代价差了一个量级，所以护栏应该偏保守。
